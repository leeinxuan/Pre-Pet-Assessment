# 新物種程式實作準則

> **用途**：本文件是把 `docs/{species}-game-planning.md` 實作成新物種流程時的強制規格。接手的 AI 必須遵守現有資料契約與共用元件，不可自行複製頁面、發明第二套架構、把物種差異寫進 JSX，或順手改動既有物種。
>
> **核心原則**：企劃決定內容；物種資料夾決定差異；共用元件決定版型與通用互動；legacy 只保留相容、不進正式流程。

---

## 1. 開始前：先讀、先盤點、再寫程式

### 1.1 必讀順序

1. `README.md`
2. `docs/AI_PROJECT_GUIDE.md`
3. `docs/AI程式碼修改準則.md`
4. 本文件
5. 目標 `docs/{species}-game-planning.md`
6. `app/data/species/index.ts`、`app/game-types.ts`
7. 一個完整物種資料夾，例如 `app/data/species/rabbit/`
8. `app/components/README.md` 與任務相關的正式元件

### 1.2 實作前必做清單

先從 planning md 整理下表；未完成前不得開始寫 UI。

| 領域 | 必須列出 |
| --- | --- |
| 選擇流程 | 顯示名稱、預設名字、品種選項、是否跳過品種頁、選擇文案與素材 |
| 準備流程 | 房間用品、危險物、位置、背景、出發用品、文件與素材 |
| 第一餐 | 互動型態、正確／錯誤食物或選項、完成規則、素材、每月費用 |
| 生活旅程 | journey item、scenario ID、stage ID、活動類型、過場、重播重設 |
| 費用 | 穩定 ID、金額、一次性／每月、觸發事件、是否為已購用品 |
| 報告 | 照護時間、回顧文案、完成項目、額外提醒 |
| 素材 | 已存在檔案、缺少檔案、可安全使用的 placeholder |

若 planning md 缺少玩家會看見的文案、費用、完成規則、照護建議或素材決策，**不要編造**。保留問題、說明缺口並請使用者確認。

## 2. 不可違反的架構規則

### 2.1 正式資料唯一入口

正式 UI 一律從以下入口取得目前物種資料：

```ts
import { getSpeciesConfig } from "@/app/data/species";

const speciesConfig = getSpeciesConfig(species);
```

新物種的內容放在 `app/data/species/{species}/`，由該資料夾的 `index.ts` 組裝，最後註冊到 `app/data/species/index.ts` 的 `speciesConfigs`。

不得把新物種正式內容寫入：

- `app/data/speciesGameConfig.ts`
- `app/game-data.ts`
- `app/life-data.ts`
- `app/data/shared/legacy-scenarios.ts`
- `app/components/life/legacy/`

它們是 legacy 相容入口。除非任務明確要求相容舊 API，否則新功能不可 import 或修改它們。

### 2.2 資料歸物種，版型歸共用元件

禁止在共用元件新增以下分支來決定物種資料：

```ts
// 禁止
species === "new-species"
isDog || isCat
item.id === "new-species-arrival"
scenario.id === "new-species-health"
const image = species === "cat" ? catImage : dogImage;
```

正確方式是先擴充資料型別，再由每個物種提供設定：

```ts
const config = getSpeciesConfig(species);
const roomScene = config.preparation.roomScene;
const feeding = config.feeding;
```

共用元件可以依通用 `activityKey` 分派既有活動元件；不可藉由物種名稱、特定 item ID 或 scenario ID 選擇素材、文案、完成條件或流程。

### 2.3 不可自行建立平行模板

- 不可複製 `page.tsx`、整個生活旅程頁、報告頁、房間頁或第一餐頁，改名後當作新物種版本。
- 不可建立 `NewSpeciesLifeJourney.tsx`、`NewSpeciesReport.tsx` 這類只服務一種動物的頁面容器。
- 不可複製既有物種文案後只替換動物名稱。
- 不可因為不知道資料放哪裡，就在元件檔案新增暫時常數或 CSS 物種 selector。

只有當既有共用契約無法表達 planning 內容時，才可新增型別、資料欄位或專屬活動；必須先說明為何現有契約不足，再做最小擴充。

## 3. 新物種資料夾的正式結構

資料夾不要求為了湊齊檔名建立空檔，但資料責任必須一致：

```txt
app/data/species/{species}/
├── index.ts                    # 組裝該物種的唯一正式設定
├── assets.ts                   # 已驗證的物種素材路徑
├── selection.ts                # 選擇頁資料（可視情況置於 index.ts）
├── copy.ts                     # 選擇、命名、流程顯示文案
├── preparation.ts              # 房間、危險物、出發用品、場景設定
├── layout.ts                   # 門牌、座標或響應式位置（需要時）
├── feeding.ts                  # 第一餐完整 FeedingConfig
├── journey.ts                  # JourneyItem、日常題目 ID、情境呈現設定
├── scenarios.ts                # Scenario、選項、回饋、忙碌照護設定
├── expenses.ts                 # 該物種唯一費用資料
├── report.ts                   # 報告與每日照護資料
├── home-readiness.ts           # 居住確認內容
├── mastered-care-themes.ts     # 報告的已建立觀念主題
├── care-review-notes.ts        # 報告額外提醒
└── {activity}.ts               # 僅供專屬活動使用的資料或狀態設定
```

### 3.1 `index.ts` 必須組裝的設定

每個物種 `index.ts` 應輸出一個類似下列的設定。欄位名稱與型別以現有物種為準，不可自行改名。

```ts
export const newSpeciesConfig = {
  id: "new-species" as const,
  selection,
  preparation,
  journey,
  scenarios,
  getLifeScenarios,
  getReportScenarios,
  scenarioPresentation,
  // breedChallenges：只有此物種真的有品種挑戰時才提供
  report,
  assets,
  layout,
  feeding,
  copy,
  homeReadiness,
  masteredCareThemes,
  careReviewAdditionalNotes,
} as const;
```

`getLifeScenarios`、`getReportScenarios` 與 `scenarioPresentation` 是旅程共用路由與報告使用的正式資料契約。不要讓中央 `app/data/species/journey.ts` 新增 `if (species === ...)` 來補新物種。

### 3.2 正式註冊清單

新增可遊玩的物種時，依序更新並檢查：

1. `app/data/shared/types.ts` 的 `SpeciesId`。
2. `app/data/shared/app-flow.ts` 的 `categories`：素材路徑必須存在，並設定正確 `active` 狀態。
3. `app/data/species/index.ts`：匯入、加入 `speciesConfigs`，並維持 `getSpeciesConfig()` 可取得它。
4. `app/data/shared/expenses.ts`：匯入 `{species}/expenses.ts`，加入 `expenseCatalogBySpecies`；正式查價一律帶入物種。
5. 相關的資料契約與測試，例如 `tests/species-data-contract.test.mjs`、`tests/species-flow-regression.test.mjs`。

以下不是新物種的正式註冊點，除非仍有外部相容需求，否則不要更新：

- `speciesGameConfig.ts`
- `game-data.ts`
- `life-data.ts`
- flat `expenseCatalog`

## 4. 使用既有共用元件的規格

### 4.1 房間與出發準備

使用 `RoomPreparation` 與 `CarTrunkPreparation`，資料放在 `preparation.ts`／`layout.ts`：

- `RoomItem`：用品、桌機／手機座標、是否必備、費用 ID、說明、素材。
- `HazardItem`：危險物、座標、危害與處理方式。
- `RoomSceneConfig`：背景、手機背景、安全狀態、門牌與場景視覺。
- `DepartureSceneConfig`：後車廂背景與文件素材。
- `TrunkItem`：出發用品、後車廂位置、費用與重用費用。

文件視覺用途必須使用 `TrunkItem.visualRole`：

```ts
{ id: "id", kind: "document", visualRole: "identity-card", ... }
{ id: "documents", kind: "document", visualRole: "document-folder", ... }
```

不可要求 `CarTrunkPreparation` 認識新物種的文件 ID。圖片尺寸差異使用 `visualScale` 或既有 `visualClassName`；互動與費用仍使用穩定 `id`。

### 4.2 第一餐

使用共用 `ArrivalMealActivity`，每個物種必須提供完整 `FeedingConfig`：

- `interaction: "scene"`：提供 supplies、unsafeFoods、scene、requiredSupplies、完成文案與 recurring expense IDs。
- `interaction: "choice"`：提供 choices、標題、引導文字、空碗文字、完成文案與 recurring expense IDs。
- 一律提供 `arrivalMealSceneLayout` 與 `arrivalMealSupplyImageSizes`。

禁止在 `ArrivalMealActivity` 加入新物種食材、危險食物、場景素材、費用或完成規則分支。

### 4.3 情境題與生活旅程

- 題目與選項放在 `scenarios.ts`；順序、`stageId`、標題與 scenario 關聯放在 `journey.ts`。
- 企劃 md 以 `**重點字**` 標記的內容，必須原樣保留在物種資料字串中，並交由既有 `renderKnowledgeText(...)`（或同等共用渲染器）輸出 `knowledge-emphasis` 重點色；不可剝除標記、直接顯示星號，或只以粗體取代重點色。若該文字目前由共用元件以純文字輸出，應優先讓該共用顯示位置支援既有重點渲染，而非在新物種元件硬寫色碼。
- 每個 `JourneyItem` 必須使用明確 `stageId`：`arrival`、`daily`、`breed` 或 `life-change`，不可依陣列 index 推斷階段。
- **頁面最上方顯示的階段眉標**由 `Scenario.stageTitle` 控制，**不是側邊欄標題**：`arrival` 使用「適應新家與安全感」，`life-change` 使用「當生活發生變化」。側邊欄階段標題一律由 `JourneyItem.stageLabel` 控制，保留 `arrival` 的「接回家」及 `life-change` 的「生活變化」；不得以頁面眉標覆寫側邊欄名稱。`timeLabel` 依既有流程提供各題時間／情境標記。
- 一般題目優先使用既有 `Scenario`、`ScenarioChoice`、`ScenarioMediaConfig` 與 `ScenarioCompletionFeedback`。
- 無物種專屬影片時，明確設定 `{ type: "placeholder" }`；不得偷用不相符的物種影片。已由產品確認可共用的過場影片除外。
- 新 journey item 必須在 `app/data/species/activity-registry.ts` 註冊 `JourneyActivityConfig`，包含既有的 `activityKey`、需要時的 `transition`、`deferItemExpenses` 與 `resetKey`。

若必須新增專屬互動：

1. 先建立物種專屬活動元件與其資料檔，放在 `app/components/life/activities/` 的適當同層資料夾。
2. 在 `app/game-types.ts` 擴充必要的 `JourneyActivityKey`、`JourneyItemType`、`LifeActivityState` 與資料型別。
3. 在 `app/data/shared/life-activity.ts` 補齊初始 state。
4. 在 `activity-registry.ts` 補齊 activity 註冊與 reset key；在 reset 策略中只重設該活動真正需要的 state。
5. 只有共用路由尚未支援這個新的 `activityKey` 時，才在 `LifeJourneyComponents.tsx` 加入一次通用分派；不得用物種名稱或 item ID 分派。
6. 補回歸測試，確認重播、下一題、完整重置與報告完成判定不改變其他物種。

### 4.3a 核心互動前導說明頁（`ActivityIntroPage`）

若企劃在核心互動活動前定義「活動前導說明頁／IntroPage」，一律使用共用
`app/components/life/activities/activity-ui.tsx` 的 `ActivityIntroPage`；不得複製成
`NewSpeciesIntroPage.tsx` 或在 `LifeJourneyComponents.tsx` 以物種名稱決定文案。

前導頁資料使用 `app/game-types.ts` 的 `ActivityIntroConfig`，放在該物種的
`journey.ts` 或只服務該活動的資料檔（例如 `{activity}.ts`）：

```ts
import type { ActivityIntroConfig } from "../../../game-types";

const dailyActivityIntro = {
  eyebrow: "日常照護",
  title: "{petName} 的活動標題",
  paragraphs: [
    "企劃指定的第一段，**重點字**保留 Markdown 標記。",
    "企劃指定的第二段。",
  ],
  startLabel: "開始今天的活動 →",
  visualAssets: {
    character: speciesAssets.daily.character,
    tool: speciesAssets.daily.tool,
    collector: speciesAssets.daily.collector,
  },
} satisfies ActivityIntroConfig;
```

- `title`、`paragraphs`、`startLabel` 與 `visualAssets` 都必須以 planning md 為準；不可把任何物種文案或素材路徑硬寫進 `ActivityIntroPage`。
- `paragraphs` 可保留 `**重點字**`；共用元件會以既有重點色呈現，畫面不可顯示 Markdown 星號。
- `visualAssets` 僅能引用該物種 `assets.ts` 已驗證的素材。企劃未要求圖片或素材缺少時可省略，或使用已核可的 placeholder；不可猜測路徑或借用另一物種主角素材。
- 在專屬活動的 `LifeActivityState` 新增明確的 `...IntroStarted: boolean`，於 `app/data/shared/life-activity.ts` 初始化為 `false`，並在 `activity-registry.ts` 的該活動 reset patch 重設為 `false`。這可讓首次進入與重玩都先顯示前導頁。
- 活動元件應在其所有 React hooks 宣告完成後，依此 state 回傳共用頁面；開始按鈕只寫入 `...IntroStarted: true`，再由 `ActivityIntroPage` 統一平滑捲動到頁首。不得在前導頁中預先完成活動、登錄費用或跳過活動初始狀態。
- 只有企劃明確需要前導頁的物種才提供上述資料與 state。未提供前導設定的物種（例如犬）自然維持原本流程；不可用 `if (species === "dog") return null` 補例外。
- 新活動若已使用既有 `activityKey`，只需由該活動元件讀取自己的資料與 state；只有缺少通用活動分派時，才依本節前述的最小擴充原則新增 `activityKey`。

### 4.4 忙碌照護與報告

- 忙碌照護資料放在 scenario 的 `busyCarePresentation`、`busyCareChecklist`、`busyCareCompletion`，協助者選項以 `isSupportChoice: true` 表示。
- 報告主架構只讀取 `getSpeciesConfig(species)` 的 `report`、`homeReadiness`、`masteredCareThemes` 與 `careReviewAdditionalNotes`。
- 第一餐完成由 `feeding.ts` 衍生；不要在報告重寫食材完成清單。
- 若新專屬活動需要出現在報告完成度，新增明確 selector key 與 selector；不要讓 `AssessmentReport` 直接判斷新活動 state 欄位。

## 5. 費用與素材規則

### 5.1 費用

- 所有金額、名稱、分類、頻率與說明只放在 `{species}/expenses.ts`。
- ID 使用小寫 kebab-case，優先採 `{species}-{purpose}`，例如 `new-species-carrier`。
- 觸發資料只引用 expense ID；UI 不可硬寫金額或 recurring 判定。
- 正式呼叫一律使用 `getExpenseForSpecies(id, species)`；查不到就視為資料錯誤，不能回退讀其他物種費用。
- 同一次事件只能登錄一次。房間、出發、情境成功回饋、重播、報告與 PDF 必須共用同一份已觸發費用紀錄。
- 臨時、醫療或高齡費用只能在對應事件成功後加入，不可載入頁面時預加。

### 5.2 素材

1. 先用 `rg --files public/assets` 驗證檔案，再使用 `/assets/...` 路徑。
2. 物種素材由 `{species}/assets.ts` 或該物種設定檔輸出；共用素材使用 `app/data/shared/assets.ts`／`public/assets/shared/`。
3. 缺少素材時使用既有 placeholder，不能建立猜測路徑或 404 `src`。
4. 不可拿另一物種的主角、身體部位、疾病或棲地素材代替新物種。
5. 若產品明確指定跨物種共用素材，必須在資料層註解原因；不可把共用決策寫進共用 JSX。

## 6. Legacy 與範圍控制

### 6.1 Legacy

- 不可刪除或任意修改 `game-data.ts`、`life-data.ts`、`speciesGameConfig.ts`、`legacy-scenarios`、`app/*-components.tsx` 或 `app/components/life/legacy/`。
- 它們不是測試頁面本身，而是保護舊 import 不失效的相容 API。
- 新正式功能不可 import legacy；除非使用者明確要求移除相容層，且已用搜尋證明沒有正式或外部使用者。

### 6.2 範圍控制

- 不改動既有物種的 ID、費用、題目、文案、座標、互動 state 或完成條件，除非需求明確要求。
- 不因為新增物種就大規模重命名、重新格式化或搬移既有元件。
- 工作區若已有不相關變更，保留它們；不可使用 reset、checkout 或覆寫清除。
- 遇到資料或設計決策不足時，停在資料層提出問題；不可自行猜測使用者意圖。

## 7. 強制驗收

### 7.1 搜尋檢查

對修改過的正式共用元件搜尋，確認沒有新增：

- `species ===`、`isDog`、`isCat`、`isRabbit`、`isBird`、`isHamster`
- 以 `item.id`／`scenario.id` 選擇物種素材、文案、流程或完成規則
- `/assets/dog/`、`/assets/cat/` 等物種素材直接路徑
- 新的 legacy import

專屬活動內可以有自己的互動 state 判斷；但若條件只是為了選資料，仍必須移至資料設定。

### 7.2 必跑指令

```bash
pnpm exec tsc --noEmit
pnpm lint
node --test tests/species-data-contract.test.mjs
node --test tests/species-flow-regression.test.mjs
pnpm run build
git diff --check
```

若指令失敗，必須明確區分本次造成的失敗與既有失敗；不可未執行就宣稱通過。

### 7.3 手動流程驗收

至少驗證新物種的：

1. 選擇物種、品種（或跳過）、命名與過往經驗。
2. 家庭與居住確認、房間危險物與用品、出發用品。
3. 第一餐正確／錯誤操作、費用觸發與重播。
4. 每一個 journey item、過場、專屬活動、上一題／下一題與重置。
5. 有前導頁的活動：首次進入、開始按鈕、重玩重設、`{petName}` 替換、Markdown 重點字與桌機／手機版面。
6. 報告完成度、費用明細、PDF／圖片輸出。
7. 桌機與手機版面；重新整理後與切換物種後不得殘留 state。

## 9. 可直接交給 AI 的指令

> 請先閱讀 `docs/AI_PROJECT_GUIDE.md`、`docs/AI程式碼修改準則.md`、`docs/新物種程式實作準則.md`、目標 planning md、`app/data/species/index.ts` 與 `app/components/README.md`。你要新增的是一個資料驅動的新物種，不是一套新網站。所有物種差異必須放在 `app/data/species/{species}/`，由 `getSpeciesConfig(species)` 提供給正式共用元件。不得複製頁面、不得在正式共用元件新增物種名稱／item ID／scenario ID 分支、不得硬寫物種素材與費用、不得使用或修改 legacy 作為正式功能。若現有契約不足，先提出最小型別與資料契約擴充方案；未取得需求依據時不得自行編造內容。完成後必須跑型別、lint、資料契約測試、流程回歸、build 與 diff 檢查，並逐項回報結果。
